# HydroFragments v0.1.0 Release-Readiness Design

## Goal

Publish HydroFragments as a coherent, installable, documented first release at
package version `0.1.0`. Remove predecessor compatibility surfaces and historical
branding while preserving useful scientific, validation, performance, and user
documentation.

## Release identity

- Package distribution and import namespace: `hydrofragments`.
- Package version: `0.1.0`.
- Configuration schema version: `1.0.0`.
- Output schema version: `1.0.0`.
- Schema versions change only when their corresponding serialized contracts
  change; package releases may change without changing either schema.
- Package metadata describes a beta-stage scientific Python product for river
  surface-water patch dynamics.

## Branding policy

README contains one lineage sentence stating that the directly preceding project
is now HydroFragments. No other tracked text, notebook content, package, module,
test, fixture, directory, filename, build artifact, or distribution member uses
either retired product name.

No compatibility import or migration facade ships in `0.1.0`. This is a hard
first-release boundary, not a deprecation cycle.

## Source architecture

The current production analysis path imports a broadly named compatibility
module even though most of that module implements current monthly section
analysis. Extract that current computation into a semantically named
HydroFragments module and update all production imports, tests, benchmark code,
comments, and function names.

Remove code that exists only to support the predecessor import namespace, wide
compatibility export, removed metric requests, and predecessor-specific input
preprocessing. Preserve current numerical behavior by moving—not redesigning—the
monthly analysis implementation and its focused tests.

Current public API remains:

- `HydroConfig`
- `HydroResult`
- `WaterCube`
- `analyze`
- `analyze_from_dea`
- `compare_results`
- `open_water_cube`
- `validate_inputs`

No new runtime feature enters this release-cleanup scope.

## Repository surface

Delete:

- predecessor package and facade-only tests;
- retired predecessor output fixtures and obsolete example notebooks;
- historical migration, quarantine, audit, pipeline, and superseded planning
  documents;
- generated build and metadata artifacts from release consideration.

Preserve and update:

- current package source and current-behavior tests;
- metric specification, renamed to a release-neutral filename and stripped of
  migration history;
- architecture, input, testing, performance, validation, manager, and metric
  coverage documentation;
- current end-to-end example and scientific validation assets;
- benchmark and validation evidence relevant to current behavior.

User-owned untracked files present before implementation remain untouched.

## Documentation and onboarding

README becomes the canonical entry point and includes:

- concise product purpose and scientific scope;
- one predecessor-lineage sentence;
- supported Python versions and install commands;
- minimal runnable quickstart using only current API;
- metric capability summary with current limitations;
- output locations and documentation links;
- citation and development-status information.

Current documentation uses release `0.1.0` where discussing the package. It uses
schema `1.0.0` only where discussing configuration, tables, or manifests. Internal
milestone numbers and release-candidate language do not appear in user-facing
copy.

Add an MIT license file and a changelog containing the `0.1.0` release. Packaging
metadata points to current repository pages, declares supported Python versions,
includes only the current namespace, and uses the license file.

## Testing strategy

Refactoring current monthly analysis follows behavior-preserving tests:

1. Rename imports and symbols in focused tests without changing assertions.
2. Move current implementation into its new module.
3. Run focused analysis, laziness, mask, parallelism, patch, and API tests.
4. Remove tests covering only deleted predecessor behavior.
5. Run complete non-slow and slow test suites.

Release checks:

- tracked-text scan finds the predecessor name only in README and finds the
  other retired name nowhere;
- tracked-path and built-archive scans find neither retired name;
- package version and installed distribution metadata equal `0.1.0`;
- config and output schema tests equal `1.0.0`;
- README quickstart and maintained notebooks pass their existing validation;
- wheel and source distribution build successfully;
- distribution metadata validation passes;
- clean temporary-environment installation imports `hydrofragments`, reports
  `0.1.0`, and exposes the documented public API.

## Failure handling

Any numerical test regression blocks release. Branding cleanup must not weaken a
current scientific assertion merely to make tests pass. If a historical artifact
contains unique current scientific evidence, extract that evidence into a
current, neutrally named document before deleting the historical artifact.

External-data and optional-GPU checks remain explicitly classified when local
credentials, network access, R packages, or CUDA hardware are unavailable. Such
environmental skips are reported separately from executable release blockers.

## Success criteria

HydroFragments is release-ready only when current source, docs, examples,
metadata, tests, and built distributions agree on the public product identity and
version; retired compatibility code is absent; required release checks pass; and
any environment-dependent checks are clearly disclosed with exact commands and
status.
